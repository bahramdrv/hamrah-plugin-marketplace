# Hamrah shared Community Signal store

Only validated, privacy-clean Signal Builder outputs belong here. Raw Telegram, forum, email, or applicant exports must not be committed.

Add datasets anywhere below `datasets/` with a `.json` extension. The publisher and deployed MCP server both inspect dataset text and locators for personal details. They index schema-valid version 2 datasets with `quality_control.personal_identifiers_removed: true` **and** a privacy `pass` decision, version 3.0.0 datasets that match the installed contract (`skills/hamrah-signal-builder/references/community_signals_v3_schema.json`) with resolvable references and both a declared and an inspected privacy pass, and version 4.0.0 Community Datasets that pass the checks below. A version 3 file with extra fields or values outside that contract is reported as invalid rather than reinterpreted.

Each supported version is adapted to canonical internal artifacts with the version 4 field names (`plugins/hamrah/mcp/community-datasets.mjs`). Every artifact keeps its `source_schema_version`; a value the original schema cannot express, such as a version 2 content hash or a version 3 fit adjustment, stays `null` or `"unknown"`. `getCommunitySignalDataset` returns `signals` in the original schema and `canonicalSignals`, `evidence`, and `sources` in canonical form. A claimed redaction flag cannot override a `fail` or `needs_review` finding. Search coverage lists excluded files with field paths and finding rules, without repeating the private value.

A version 4.0.0 dataset (`skills/hamrah-signal-builder/references/community_dataset_v4_schema.json`, example `skills/hamrah-signal-builder/examples/v4_signal_dataset.json`) keeps Sources, Evidence, Signals, Questions, Academic Opportunities, Lived Experiences, and Route Claims in separate collections linked by IDs. `plugins/hamrah/mcp/community-dataset-v4.mjs` rejects the whole file when an ID is duplicated or a reference does not resolve; when evidence lacks `retrieved_at` or a `content_hash`; when a public source lacks an HTTPS locator or private-source evidence carries one; when a date is impossible or after `generated_at`; when any artifact's `validation` is not `validated` with privacy `pass`; or when privacy inspection does not pass. Stale and superseded artifacts remain in the file for history and are excluded from default search.

The privacy decision includes audited exceptions for institution names and exact domain phrases. Review the reported field and source before correcting a finding; automatic detection can miss names or context. Remove private material from the candidate before rerunning the publication command.

## Seeded German evidence

The first published dataset (`datasets/2026/09/20260925174655-de-study-opportunity-card-78f7f8bd21.json`) covers German study routes (`student_bachelor`, `student_masters_taught`, `student_masters_research`, `student_phd`) and the `opportunity_card`. It was retrieved on 2026-09-25 from Residence Act sections 2, 16b, and 20a (gesetze-im-internet.de), the Federal Foreign Office blocked-account page, and German embassy in Tehran notices, and published through the same command and gates as later data. Official rules are Route Claims; the embassy's restricted visa operation and the closed Iranian airspace are officially confirmed Signals for applicants resident in Iran, flagged for recheck by 2026-10-09. Every artifact links evidence with primary authority, an HTTPS URL, retrieval time, and a SHA-256 hash of the retrieved page. Facts the sources did not state, such as the study blocked-account amount and which Tehran waiting list covers the Opportunity Card, are recorded in the watchlist as unknown rather than claimed. Search for any other country or route reports `coverage.status: "no_coverage"`, which means missing coverage, not a closed route.

`searchCommunitySignals` also returns `routeClaimCoverage` (matching Route Claims by `countryCode`, route, process stage, and topic; a country name, origin, nationality, or entity filter cannot be checked against a claim, so claims are then not counted and the filter is listed in `notEvaluated`), and `getCommunitySignalDataset` returns each dataset's `routeClaims` with their evidence.

## Community Questions

Questions are published with the same command. A model may propose which phrasings belong to one Question by listing them as `variants`; publication then decides deterministically (`plugins/hamrah/mcp/community-questions.mjs`). Records whose normalized English canonical text and scope match receive the same stable ID and are merged, with variants, evidence, and seen dates combined; conflicting answer status, trend, Persian canonical text, or lifecycle stops publication. Each record's `independent_asker_count` must equal the number of distinct askers in its evidence, where posts in one independence group or with the same content hash count once, and the published count is recomputed after merging. The same wording assigned to two Questions with overlapping country and route scope is an unresolved merge and is refused as `needs_review`, as is any candidate that declares a `needs_review` validation state. The reader re-checks counts and ambiguity. `searchCommunityQuestions` and `getCommunityQuestion` read them, normalizing Persian letter variants, diacritics, digits, and punctuation.

## Route Claims

Route Claims are published with the same command, with or without Signals. `claim_type` is one of `official_rule`, `financial_requirement`, `operational_pattern`, `anecdotal_pattern`, `opportunity`, `risk`, or `workaround`; only the first two can describe official rules. An optional `applicant_scope` (the Signal applicant-scope structure) limits a claim to listed nationalities, residence or applying-from countries, or origins, and joins the claim's identity only when present. `searchRouteClaims` (`plugins/hamrah/mcp/community-route-claim-tools.mjs`) filters by country, route, stage, claim type, applicant, and text; an unscoped claim matches every applicant. Each result lists supporting and opposing evidence classed as `official` (primary or trusted authority from a public HTTPS source), `public_community`, or `private_community` (whose locator is never returned), with retrieval, publication, and event dates, and a verification status taken from the strongest supporting class.

## Evidence Confidence

`validateRouteClaim` (`plugins/hamrah/mcp/community-claim-confidence.mjs`) scores one Route Claim from 0 to 100 under `skills/hamrah-signal-builder/references/evidence_confidence_policy.json` (version 1.0.0): source-family diversity (15, counted at most once per independent report), independent public reports (25; one report scores 5), primary or trusted public support (25), recency of the newest public support against the claim type's window (15), fit with a supplied applicant (10), and data quality (10), minus 10 per independent public opposing report up to 30. Labels are very_low below 25, low below 50, moderate below 75, and high from 75. Copies, cross-posts, shared independence groups, and shared URLs count once. Only public evidence scores; private evidence is reported as context. Opposing evidence stays listed, and explanations for a contradiction (timing gap, differing source populations, official rule versus practice) are returned only as labelled hypotheses. The weights and windows are initial values chosen before evidence review and must be revised by a new policy version.

## Academic Opportunities

Opportunities are published with the same command as separate artifacts. Each has country and routes, institution, department, program, degree level (`bachelor`, `master`, `phd`, `postdoc`, `other`), field, research area, and a public supervisor or chair when the source names one, a deadline and intake, funding with typed components (stipend, tuition waiver, assistantship, scholarship, salary position), admission conditions, nationality restrictions, and Iranian evidence status. Unknown facts are `null` or `unknown`; admission conditions are `null` when no source states them. Publication (and the reader) require verified funding to have a verified component with evidence, verified conditions and restrictions to cite evidence, and `explicit_public_evidence` of Iranian participation to cite only public evidence; nested evidence references must resolve. `searchAcademicOpportunities` and `getAcademicOpportunity` (`plugins/hamrah/mcp/community-opportunity-tools.mjs`) return stable IDs, classed evidence, freshness, and explicit coverage.

Verification happens at read time against an `asOf` date (default today) in `plugins/hamrah/mcp/community-opportunity-verification.mjs`. An official institution source is primary or trusted evidence from a public HTTPS university, government, or employer source; publication requires one for every funding component declared `verified`. The deadline, cited through `deadline_evidence_ids`, is `open`, `expired`, `unverified` (no official source), `needs_reverification` (official source older than the scorecard freshness policy's `deadline` limit), or `unknown`; an expired deadline makes the opening `historical`, which default search excludes. A funding component is effectively `verified` only with a current official source under the `financial_requirement` limit and no official contradiction in its `opposing_evidence_ids`; community disputes are kept and lower confidence to medium, while conflicting official sources, stale sources, or community-only support leave it `unknown`. Nationality restrictions count only with official evidence. The `fundingStatus` search filter uses the verified state: `verified` and `none` as verified, `unverified` for funding a source reports but nothing verifies, and `unknown` when no funding is reported.

## Iranian Lived Experiences

A Lived Experience records one Iranian applicant's milestone, refusal, delay, operational failure, withdrawal, or bare claim, with country, routes, event date, entity, applicant scope, and a short anonymized `summary_en`. Publication and the reader (`plugins/hamrah/mcp/community-experiences.mjs`) require an `iran_connection` with status `explicit` and basis `self_declared` or `documented`, cited only by public evidence whose summary states the connection ("Iran", "Iranian", or the Persian word); a name, appearance, language, or education history leaves Iranian status unknown and the candidate is refused. Milestones are fixed per family (study: admission_received, study_visa_granted, enrolled; work: job_offer_received, work_visa_granted, employment_started; settlement: permanent_residence_granted, citizenship_granted; process: application_submitted, appointment_obtained, interview_attended). A process step can never be `milestone_attained` and stays `claim_only`, and an attained milestone needs public evidence; only attained study, work, or settlement success milestones are qualified successes. A refusal, delay, or operational failure needs an event date and a public source link. A profile URL that looks like a personal name is allowed only on evidence marked `public_person_locator` that a Lived Experience cites, and on the source behind it; each use is recorded as a `public_person_locator` privacy exception, and names elsewhere in the text are still refused.

`searchIranianLivedExperiences` and `getLivedExperience` (`plugins/hamrah/mcp/community-experience-tools.mjs`) filter by country, route, milestone, outcome, applicant nationality or residence, and text, and return stable IDs, the Iran connection basis and evidence IDs, classed evidence, verification, and freshness (last verification, newest retrieval, event date). Evidence marked `public_person_locator` is shown as `public_person` with its source family but no URL, private community evidence has the role `context` and no locator, and public evidence that contradicts the case has the role `opposing` and never counts as support. Each case is classed `qualified_success` (an attained study, work, or settlement success milestone), `failure` (refusal or operational failure), or `unresolved` (delays, progress milestones, withdrawals, bare claims, and cases left with only opposing public evidence). When, after withdrawals, a case's milestone or Iran connection rests only on private community evidence it is `private_context`, which is never counted as a public success or failure. Search adds `observedCases` over every match with the per-class counts and IDs, a sample-bias statement, and `usable_as_probability: false`; no ratio or rate is computed.

## Official approval statistics

An optional `official_statistics` collection records approval statistics exactly as an authority publishes them: country and routes, the publishing authority, a population (`description_en` plus an applicant scope), a period, and `applications`, `approvals`, and `refusals` counts. Each count carries the population and period its table states, and `published_success_rate` holds the authority's own percentage or `null`. Publication and the reader (`plugins/hamrah/mcp/community-official-statistics.mjs`) refuse a statistic when any cited evidence is not an authoritative public source (primary or trusted authority, HTTPS, and a government, immigration-authority, or embassy source type), so community samples can never be official statistics. They also refuse one when a period is invalid, starts after it ends, or ends after `generated_at`; when neither approvals nor refusals are given; when matching approvals or refusals (or their sum) exceed applications; or when `published_success_rate` is given with zero applications or differs by more than 0.1 percentage points from both approvals / applications and approvals / (approvals + refusals). A dataset without the collection omits it, so older content keeps its digest.

`searchOfficialApprovalStatistics` (`plugins/hamrah/mcp/community-statistics-tools.mjs`) filters by country, route, and applicant scope. It computes `official_success_rate` and `official_refusal_rate` (percent, one decimal) only from counts whose population and period match the statistic's and the applications count. A missing or zero denominator, a missing approvals count, a mismatched population or period, or no remaining authoritative source leaves the rate `null` and lists coded `reasons`. A statistic is `official` only when `official_success_rate` is computed, so a refusal-only statistic stays `unresolved` even though its refusal rate is shown. A published rate is never copied in place of the counts. Each result names its authority, population, period, and authoritative sources, and the response's `separation` statement keeps the statistic apart from IRVI, applicant fit, Practical Fit, Evidence Confidence, and Community Confidence.

## Iranian Route Viability Index

`getIranianRouteViability` (`plugins/hamrah/mcp/community-route-viability.mjs`) assesses one country and route for a profile explicitly connected to Iran by nationality, residence, or origin, under the versioned rubric in `skills/hamrah-signal-builder/references/irvi_policy.json`. Policy 0.1.0 was reviewed against the initial German study and Opportunity Card dataset on 2026-09-25. It remains `provisional` and caps confidence at `low` because that seed has no Lived Experiences or Academic Opportunities for calibrating those components. Each evidence-based component exposes public evidence IDs, artifact IDs, source URLs, retrieval dates, and freshness status. Components are:
- official accessibility (20): current public official Route Claims with primary or trusted support, aged by the scorecard freshness policy; stale or officially contradicted rules earn 0;
- profile compatibility (15) and execution practicality (15): caller-supplied `high`, `medium`, or `low` from the applicant's scorecard facts;
- Iran-specific evidence (15): current public Route Claims and Signals scoped to Iranian nationals, residents, or applicants from Iran; an officially supported Iran-scoped risk earns 0;
- qualified examples (10): recent qualified successes among public Iranian Lived Experiences;
- funding or sponsorship (10): verified funding among current Academic Opportunities;
- evidence quality (15): the route claims' mean Evidence Confidence.

Components with no input are `not_assessed` and are left out of the base, which is rescaled to 100. Community friction from applicable, current Signals with public evidence is then subtracted (at most 20 points); private-only Signals and Signals with unknown freshness are listed as separate warnings and do not score. A route with no current official basis has no score and is `research_required`. Confidence reports why it is limited: provisional policy, components not assessed, stale or conflicting official data, or no recent qualified example. Official eligibility, applicant fit, and Practical Fit (echoed from the caller's scorecard), Community Confidence, IRVI, and official approval statistics are separate fields, and scorecard values never enter IRVI.

## Route Evidence Thresholds

The reviewed version 1.0.0 policy in `skills/hamrah-signal-builder/references/route_evidence_thresholds.json` configures separate thresholds for German bachelor, taught master's, research master's, PhD, and Opportunity Card routes. The four study routes require two current official source families; the Opportunity Card requires one. All five require two independent, current, public Iran-scoped source families and at least one recent qualified attained milestone. The values were reviewed against the first published German dataset: study routes have two official source families, the Opportunity Card one, but every route has just one Iran-scoped family and no qualified examples. They therefore remain unranked with the exact missing requirements exposed in `ranking.threshold`. Other routes return `unconfigured` and remain unranked.

The threshold decision lists requirements, observed families and evidence IDs, and missing evidence. Public records sharing an independence group or content hash count once; private reports, stale evidence, and high-copy-risk records never satisfy an independent public requirement. Ranking also requires official eligibility `PASS`, a current official basis, and no unresolved official requirement or conflicting public evidence. IRVI may remain numeric when ranking is blocked; neither IRVI nor observed examples are approval probabilities.

## Viable route discovery

`findViableRoutesForIranians` uses a bounded EvidenceProvider backed by the validated Git dataset store to discover source-backed legal-route candidates for up to four requested ISO alpha-3 countries. The provider identifies candidates from public primary or trusted Route Claim sources, including candidates whose official facts need rechecking; it does not infer an individual's eligibility. The caller may supply up to ten prior per-route scorecard assessments in `routeAssessments`, but a caller-supplied `PASS` remains unverified and cannot unlock ranking. A trusted `eligibilityProvider` integration must return a current, verified assessment with an ID and source IDs; without it, candidates remain unranked. The tool assesses at most ten candidates, reuses the loaded store, and keeps ranked and unranked results separate. Results expose a public evidence trace, freshness, verification, privacy status, and coverage. Ranking follows the same IRVI and Route Evidence Threshold gates as the single-route tool.

`getIdealCandidateProfile` inspects one country and route in the validated store. It labels current authoritative Route Claims as `official_requirement`, public operational or anecdotal claims as `community_pattern`, and non-sensitive characteristics explicitly stated in the public evidence of qualified successful Lived Experiences as `observed_success_pattern`. Each displayed characteristic carries its source and freshness; public person profile URLs remain withheld. Conflicting or stale claims appear in `unresolved`, and missing evidence returns `no_coverage`. The Persian notes explain that observed examples are neither mandatory requirements nor approval probabilities. An official rule still needs an individual applicability check.

Each candidate reports its reasons, risk signal IDs, qualified example count, evidence IDs, next research actions, confidence, and a Persian summary. Country coverage distinguishes `covered` from `no_coverage`; a country with no validated source-backed candidate is not treated as having a closed route. A failed EvidenceProvider returns `research_required`, with empty ranked and unranked lists. Source IDs and scorecard statuses retain their origins; the tool does not convert a route-finder ordering score or community observations into official eligibility or approval probability.

## FAQ answers

A Question may list `answer_links` to Route Claims or Signals that answer, partially answer, or contradict it; links may name artifacts already published in another dataset, and publication refuses links that resolve nowhere. `answerCommunityQuestion` (`plugins/hamrah/mcp/community-answers.mjs`) takes the newest copy of each linked artifact and excludes it when it is missing, not current, out of the question's country or route scope, stale, or of unknown freshness. Route Claim freshness uses the scorecard's versioned fact-type policy (`official_rule` maps to `statutory_condition`) measured from the newest evidence retrieval; Signal freshness uses its `suggested_recheck_date`. An answer is `official` only when a remaining Route Claim has primary or trusted authority from a public HTTPS source; community contradiction then lowers confidence to medium, and an official contradiction makes it `unresolved`. Without an official rule, conflicting community support is `unresolved`, two or more independent public sources are `evidence_based`, and anything less is a `community_observation`; copies count once. Partial-only support is `partially_answered`, only-stale support is `outdated`, and no usable evidence is `research_required`. Each answer lists citations with authority, URL, retrieval time, and content hash, excluded links with reasons, a Persian explanation, and the last verification date. Pass `asOf` for reproducible freshness checks.

## Cross-dataset evidence

`searchCommunitySignals` returns `evidenceAggregation` for the requested scope across every valid dataset (`plugins/hamrah/mcp/community-aggregation.mjs`). Records that share a version 4 ID, content hash, normalized summary text, or message locator form one evidence cluster, so cross-posted copies are listed together with their source families, copy risk, and time window. Clusters are one independent report when a dataset declares a shared independence group or they cite the same URL. Only records linked from active, monitoring, or uncertain signals, and not superseded by newer evidence, count toward `currentSupport`; historical, stale, resolved, and superseded records stay in `clusters` with a `historicalReason`. Contradicting records are kept and counted separately, each signal reports its own `evidenceSupport`, and `datasetCoverage` names the matching datasets with their sources and coverage. Text matching is exact after normalization; paraphrased copies are not yet detected.

## Publishing version 4 evidence

Version 4 data is published only through the explicit command below, from the repository root. The candidate uses the version 4 layout with local keys as IDs (validation blocks are optional; a declared `needs_review` or non-`pass` state is refused):

```sh
node plugins/hamrah/mcp/community-publication.mjs publish candidate.json \
  --store-root plugins/hamrah/data/community-signals \
  --label telegram-de-student
```

`--store-root` is required. The report states `readerScans: true` only for this deployed store; any other root is a local store the deployed server never reads. Publication runs the normalization, deduplication, privacy, provenance, evidence, contradiction, and schema gates, printing each failure as `[gate] message` and writing nothing when any gate fails. Artifact IDs are SHA-256 digests of normalized identity fields (source locator or family, content hash, country, routes, claim or question text, event date, and entity as applicable), so re-importing the same material yields the same IDs, and re-importing unchanged content is a no-op. Each changed import adds a new immutable snapshot under `datasets/`; search uses the newest copy of each signal, so a later `superseded` or `resolved` snapshot hides the older current one.

To withdraw an artifact or a whole snapshot after a later review, append to the ledger:

```sh
node plugins/hamrah/mcp/community-publication.mjs withdraw \
  --store-root plugins/hamrah/data/community-signals \
  --artifact evd_<id> --reason privacy --note "Direct identifier found."
```

Use `--dataset <datasetId>` for a whole snapshot. Reasons are `privacy`, `incorrect`, `superseded`, or `other`. `withdrawals.json` is append-only and published snapshots are never rewritten; the server removes withdrawn artifacts from search and retrieval, drops a signal left with no evidence, and fails closed if the ledger is unreadable. Because Git keeps history, a privacy withdrawal hides content from Hamrah but does not erase it from the repository.

Version 2 and version 3 datasets can still be stored with `skills/hamrah-signal-builder/scripts/store_signals.py`, which refuses version 4 input. Commit and push the generated `datasets/` file, `catalog.json`, and any `withdrawals.json` change. Vercel deploys the repository revision; then refresh Hamrah in ChatGPT so it reloads the updated tool inventory. The runtime scans `datasets/` directly, so a stale or missing `catalog.json` cannot hide a valid dataset.
