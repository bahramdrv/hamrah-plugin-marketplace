# Visa Atlas MCP access

The active contract is `visa_atlas_core_openapi.json` (version 1.3.0). The plugin's `.mcp.json` starts a local `visa-atlas` MCP server and builds its tool inventory and route-finder request schema directly from that curated contract. The server only calls fixed paths under `https://visaatlas.org`; it does not accept arbitrary URLs. Public GET tools need no applicant data.

Currently the bundled API contract covers Visa Atlas only. Other official sources can be read through their verified primary URLs. If the user supplies additional API contracts, follow their documented endpoints and authentication using the host's supported tools; do not assume unnamed APIs or credentials exist. Keep separate source identities, retrieval dates, effective dates, and conflicts for each program. Refresh relevant live sources for each new assessment; a bundled contract's date does not establish record freshness.

Prefer the namespaced MCP operations when available: `getVisaRoutes`, `getDestinations`, `getPolicyUpdates`, `getPolicyClaims`, `getVisaFees`, `getCostToComplete`, `getSalaryThresholds`, `getProcessingTimes`, and the other operation IDs in the contract. GET tools accept optional local filters (`destination`, `countryCode`, `slug`, `category`, `query`, and `limit`) so only relevant records enter the conversation. If MCP is unavailable, use a host HTTP/browser tool against the exact documented endpoint and disclose the fallback.

Retrieve only relevant datasets: visas and destinations for screening; policy-updates and policy-claims for changes; salary-thresholds, fees, processing-times and cost-to-complete for practical requirements; calculator-verdict-contexts and Express Entry datasets when relevant. Use `getVisaAtlasCatalog` to confirm live dataset availability and inspect individual record dates and government links.

Use `getRouteFactPack` when several of its approved public datasets are needed for one route. Supply an ISO alpha-2 `countryCode` (for example `DE`, not `DEU`), the exact route slug, and 1–6 dataset operation IDs from `getVisaRoutes`, `getDestinations`, `getPolicyUpdates`, `getPolicyClaims`, `getVisaFees`, `getCostToComplete`, `getSalaryThresholds`, `getProcessingTimes`, `getSourceFreshness`, and `getProcessingReliability`. The tool accepts two input forms for the same operation: `{countryCode, routeSlug, datasets}`, or `{countryCode, slug, datasets?}`, where `slug` is an alias for `routeSlug` and omitted `datasets` default to `getVisaRoutes`, `getPolicyClaims`, `getPolicyUpdates`, `getVisaFees`, `getSalaryThresholds`, and `getProcessingTimes`. Both forms fetch concurrently under one deadline and give each dataset a `success`, `failure`, or `timeout` status; when the deadline expires, completed datasets are returned and the rest are marked `timeout`. `coverage` counts `successful`, `failed`, and `timedOut` datasets against `denominator`, the number of datasets selected for the call (`denominatorBasis: "datasets_selected"`); `percentage` is successful datasets divided by that denominator. It is not a measure of legal certainty or route evidence completeness. The pack `status` is `partial` or `all_selected_retrieved` and is never `complete`: even a pack with every selected dataset retrieved is not a complete route assessment. The tool scans at most 500 records per dataset and reports `scanLimited` and a partial pack if this cap is reached, even when retrieval coverage is 100%. Keep the source metadata on returned records; if a dataset fails or times out, report its facts as unavailable rather than empty.

Use `searchCommunityQuestions` to find recurring applicant questions in Persian or English for a country, route, topic, or stage, and `getCommunityQuestion` with the returned `questionId` to inspect the posts behind it. Independent asker counts collapse repeated posts by one asker and cross-posted copies; they measure how often a question is asked, not its answer. Use `answerStatus` to see whether an answer is established; a question is never evidence of a rule, and `no_coverage` means unknown. Call `answerCommunityQuestion` with the `questionId` for a cited answer: `official` only when a current Route Claim has an authoritative public source; `evidence_based`, `community_observation`, `partially_answered`, `outdated`, `unresolved`, or `research_required` otherwise. Present the answer type, confidence, citations, and last verification date, keep official rules separate from community observations, and never turn `research_required` into a negative answer.

Use `searchRouteClaims` to find Route Claims by country, route, stage, claim type, applicant nationality or residence, or text. Present each as a sourced statement, not a fact: show its claim type, verification status (`official_source`, `public_community_source`, or `private_community_only`), supporting and opposing evidence with their classes and dates, and applicant scope. Only `official_rule` and `financial_requirement` claims describe official rules; patterns, opportunities, risks, and workarounds never do. Call `validateRouteClaim` with the `claimId` (and the applicant's nationality or residence when known) for its versioned 0–100 Evidence Confidence. Show the score with its label, every component, the contradiction penalty, the scope-limited explanation, and any limitations; present contradiction explanations only as hypotheses, and never describe the score as an approval chance.

Use `searchAcademicOpportunities` to find validated academic openings by country, route, institution, degree, field, funding, deadline, or text, and `getAcademicOpportunity` for one opening's full record, classed evidence, and freshness. Report funding, admission conditions, nationality restrictions, and Iranian evidence exactly as stated; `unknown` or `null` means no source states it, and a deadline filter reports how many openings with unknown deadlines it left out. Never infer funding or eligibility from community discussion. Use each result's `verification`: report funding as available only when its effective status is `verified`, say a deadline has passed when it is `expired`, and ask the applicant to re-check the institution page for `unverified` or `needs_reverification` deadlines.

Use `searchIranianLivedExperiences` to find public Iranian Lived Experiences by country, route, milestone, outcome, applicant nationality or residence, or text, and `getLivedExperience` for one case's full record, classed evidence, verification, and freshness. Never name or try to identify the person, and do not look up withheld profile locators. Present `observedCases` as biased observations: show qualified successes, failures, and unresolved cases side by side with the `sampleBias` statement, and never divide them into a success rate, approval chance, or probability (`usable_as_probability` is always false). A `private_context` case or `context` evidence is background or a warning only; never present it as a public success.

Use `searchOfficialApprovalStatistics` for approval statistics an authority publishes for a defined population and period. Quote `official_success_rate` only when the statistic's `status` is `official`, and always with its authority, population, period, and source link. For an `unresolved` statistic, say that no official rate is available and give its reasons; never substitute its `publishedSuccessRate`, a community sample, or Lived Experience counts. Keep an official statistic separate from IRVI, applicant fit, Practical Fit, Evidence Confidence, and Community Confidence, and do not apply a statistic whose population is broader than the applicant's as if it were theirs.

Use `getIranianRouteViability` for one route's Iranian Route Viability Index. Pass at least one explicit Iran connection in the applicant's nationality, residence, or origin; the tool rejects profiles without it. When the scorecard has assessed them, pass `profileCompatibility`, `executionPracticality`, `officialEligibility`, `applicantFit`, and `practicalFit`. Present IRVI as route viability with its confidence label, every component with its points, detail, and public evidence trace, the friction, the policy version and provisional status, and the ranking reasons. Report the separate `ranking.threshold` policy version, reviewed date, requirements, observed public source families, and missing evidence; say plainly that the route is unranked when `rankable` is false. Ranking requires official eligibility `PASS` plus a passed route threshold. Report official eligibility, applicant fit, Practical Fit, Community Confidence, and official approval statistics in their own places, never combined with IRVI, and never call IRVI a visa chance or approval probability.

Use `findViableRoutesForIranians` to compare source-backed candidates across up to four destinations. Pass an explicit Iran connection and only prior scorecard results in `routeAssessments`; caller-supplied eligibility remains unverified and cannot unlock ranking. A trusted current eligibility assessment is required for a ranked result. Show `ranked` separately from `unranked`, with the latter's missing gates and country `no_coverage` statuses. Cite each result's public evidence trace, freshness, verification and privacy status, confidence, risks, qualified example count, and next actions, and use its Persian summary. An unavailable EvidenceProvider returns `research_required`; do not fill gaps with guessed routes or outcomes. The tool assesses at most ten candidates and does not use the Visa Atlas route-finder ordering score as eligibility or probability.

The supplied 1.3.0 contract includes `freshness`, `citation-packs`, and `answer-capsules`. During integration testing on 2026-09-14 those three paths returned HTTP 404 and were absent from the live catalog. Do not treat them as available until a later live call succeeds. If `getSourceFreshness` fails, use catalog `dateModified`, record review dates, and primary-source verification instead.

Visa Atlas is a source-linked compilation, not a government authority. Check the linked primary source for decisive requirements, stale records, and contradictions. Retain Visa Atlas attribution, canonical URL, government-source URL and record dates. A successful HTTP response is not proof of current legal accuracy.

Optional route discovery uses `getRouteFinderContract` and `findMatchingVisaRoutes`. Before the POST tool, tell the facilitator that a coarse subset of the profile will be sent to Visa Atlas and obtain explicit consent once. Send only supported fields that are known and necessary. Omit unknown fields. Never transmit the full applicant profile. Do not infer currency bands or language equivalences. Route-finder ordering scores are candidate-discovery aids, not Hamrah Base Fit or official eligibility.

Handle timeout, HTTP errors, malformed JSON, missing tools and insufficient evidence explicitly. Keep official context partial and affected eligibility UNKNOWN when necessary. Do not fabricate responses. Read-only browsing can support GET datasets if a POST tool is unavailable.

This plugin replaces the GPT Action with a callable local MCP adapter. A future ChatGPT web publication still requires deploying the same MCP behavior to a stable public HTTPS endpoint; the local stdio server is for Codex installations.
