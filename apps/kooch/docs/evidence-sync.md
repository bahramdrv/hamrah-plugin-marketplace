# دریافت و بازبینی شواهد عمومی — تیکت ۰۸

## قرارداد و حدود اختیار

افزونهٔ مستقل `source/wordpress/kooch-evidence-export.php` در کنار `kooch-visa-data` نصب می‌شود؛ فایل‌های افزونهٔ قبلی و snapshot منتشرشده را بازنویسی نمی‌کند. endpointهای فقط‌خواندنی ثابت عبارت‌اند از `https://kooch.app/wp-json/kooch/v2/evidence-manifest` و `evidence-page/<sha256>/<index>` در همان namespace. query، URL دلخواه، redirect و payload متقاضی پذیرفته نیستند. فیلدهای عمومی با allowlist صادر می‌شوند؛ نام/تماس/حساب یا payload کامل کاتالوگ ضمیمه نمی‌شوند.

قرارداد نسخهٔ ۱، دامنهٔ `iran-start`، نگاشت `iran-start-route-key-1` و سیاست `iran-channel-14-days-1` دارد. هویت مصرفی، route key بازبینی‌شده است؛ تغییر slug ارائه‌دهنده بدون نگاشت بازبینی‌شده به حذف/افزودن و صف بررسی منجر می‌شود، نه اتصال حدسی به قواعد قبلی. page_url فقط HTTPS با مبدأ `kooch.app` و مسیر `/visas/` پذیرفته است.

Manifest یک رشتهٔ JSON عمومی و SHA-256 همان بایت‌ها دارد. درون آن، شمار کل، آمار پوشش، منابع با تاریخ اصلی و فهرست index/count/hash صفحه‌هاست. payload رشته‌ای هر صفحه جدا هش می‌شود؛ شناسهٔ برداشت در envelope نیز باید با manifest یکسان باشد. این هش‌ها تمامیت و اتصال صفحه‌ها را کنترل می‌کنند و تأیید حقوقی یا امضای ناشر نیستند. تمام صفحه‌های یک برداشت از کپی ثابت وردپرس می‌آیند؛ دریافت اولیه در تراکنش خواندن سازگار انجام می‌شود. انقضای کپی ۴۸ ساعت است؛ cursor قدیمی ۴۱۰ می‌گیرد و هرگز به صفحه‌های نسخهٔ تازه هدایت نمی‌شود.

حداکثر ۵۰۰ مسیر، ۲۵ صفحه، ۲۰ مسیر در هر صفحه، پاسخ ۲MB و مجموع checkpoint هشت MB است. هر اجرای worker یک صفحه می‌گیرد؛ manifest و خواندن stream در همان مهلت ۲۵ثانیه‌ای شبکه هستند. SQL و اتصال نیز کران مستقل دارند و مسیر میزبان حداکثر۳۰ثانیه است. retry شبکه در همان اجرا وجود ندارد. قطع وسط اجرا، قفل worker یا خطای شبکه، نسخهٔ فعال را عوض نمی‌کند. worker بعدی از checkpoint هش‌سنجی‌شده ادامه می‌دهد؛ manifest منقضی از ابتدا جایگزین می‌شود؛ پاسخ۴۱۰صفحه نیز فقط checkpoint را پاک می‌کند تا اجرای بعدی manifest تازه بگیرد. چند instance با قفل advisory تراکنشی مشترک از تکرار هم‌زمان صفحه جلوگیری می‌کنند.

## نامزد، نسخهٔ فعال و کارنامه

migration `006-evidence-sync.sql` فقط جدول دادهٔ عمومی/وضعیت را با RLS اجباری و دسترسی نقش server اضافه می‌کند؛ نقش پرونده به آن دسترسی ندارد. snapshot بسته‌بندی‌شده، baseline بازبینی‌شده است. نامزد کامل و آخرین snapshot سالم در PostgreSQL مشترک ذخیره می‌شوند؛ نوشتن فایل روی دیسک serverless انجام نمی‌شود. active تا کامل‌شدن همهٔ صفحه‌ها تغییر نمی‌کند.

نام، برچسب و page_url توصیفیِ معتبر برای هویت شناخته‌شده قابل به‌روزرسانی‌اند. تغییر application، شرط/هزینهٔ facts، خلاصهٔ تصمیم‌ساز، منابع/تاریخ بازبینی، یا افزودن/حذف مسیر، صف بازبینی می‌سازد. مقدار تصمیم‌سازِ نامزد به baseline یا قواعد رسمی منتقل نمی‌شود. مسیر مربوط از قطب‌نما کنار می‌رود؛ کارنامهٔ ذخیره‌شده ثابت می‌ماند ولی wrapper خواندن نیازمند بازبینی می‌شود. گزارش تازه از آن مسیر نتیجهٔ سازگار یا مبلغ عمومی قطعی نمی‌سازد. خطای sync یا نبود دسترسی به وضعیت شواهد نیز گزارش را نیازمند بازبینی می‌کند؛ این حالت به‌عنوان خطای دریافت توضیح داده می‌شود و ادعای تغییر قطعی شرط نمی‌کند. خواندن شواهد داخل تراکنش پرونده از همان اتصال استفاده می‌کند و نقش محدود پیش از ادامه برمی‌گردد؛ pool دوم لازم نیست. انقضا در هر match/report و صفحهٔ وضعیت دوباره محاسبه می‌شود؛ اجرای دقیق cron شرط ایمنی نیست و کاتالوگ کامل fallback نمی‌شود.

دریافت موفق زمان retrieval را ثبت می‌کند؛ checked_on، valid_until، checked_at و expires_at شواهد رسمی را تمدید نمی‌کند. قواعد کارنامه در `src/report/policy.ts` همچنان نسخهٔ بازبینی‌شدهٔ مستقل‌اند. رفع صف نیازمند بررسی منبع اولیه، اصلاح baseline/قواعد لازم در یک release بازبینی‌شده، و اجرای sync است؛ کلیک مدیر یا دریافت Atlas، تأیید رسمی تازه نمی‌سازد. GET `/api/evidence/candidate` با کلید مدیر، نامزد عمومی کامل را برای این مقایسه می‌دهد. برداشت دوبارهٔ همان manifest نیز صف را بدون تغییر baseline پاک نمی‌کند.

## مدیریت و زمان‌بندی

`/admin/evidence` وضعیت آخرین تلاش/دریافت کامل، پوشش جاری، انقضا، checkpoint و صف بازبینی را نشان می‌دهد. GET `/api/evidence/status` و `/candidate` کلید مستقل `KOOCH_EVIDENCE_ADMIN_SECRET` می‌خواهند. POST `/api/evidence/sync` کلید متفاوت `KOOCH_EVIDENCE_SYNC_SECRET` می‌خواهد. هر کلید حداقل۴۳نویسه، بدون NEXT_PUBLIC، و هرگز یکسان نیست. حساب عادی و cookie آن اختیار مدیریت نمی‌دهند؛ کلید فقط در header و حافظهٔ موقت فرم مصرف می‌شود. پاسخ‌های مدیریت no-store هستند؛ هیچ کلید در URL، log، storage مرورگر یا snapshot ثبت نمی‌شود. رابط مدیر فقط‌خواندنی است.

Workflow `sync-kooch-evidence.yml` روزانه ساعت۰۳:۱۷UTC (۰۶:۴۷تهران) و با workflow_dispatch قابل اجراست. قبل از پیکربندی، با متغیر repository به نام `KOOCH_EVIDENCE_SYNC_ENABLED` غیرفعال است. زمان‌بندی به بازدید وردپرس وابسته نیست و تأخیر یا ازدست‌رفتن اجرا با freshness هنگام مصرف کنترل می‌شود. سرویس پولی، پلن تازه یا ارتقا ایجاد نمی‌کند؛ فعال‌سازی فقط پس از تأیید سهمیهٔ Actions و محیط انتشار در تیکت۱۰ است.

فرمان بازیابی دستی از همان worker استفاده می‌کند:

```sh
# کلید را فقط از محیط امن خود وارد کن؛ مقدار واقعی در فرمان یا Git نباشد.
npm run evidence:sync
# نام قدیمی هم به همین مسیر امن متصل است:
npm run refresh:data
```

پیش‌فرض origin فقط `https://my.kooch.app` است؛ برای محیط آزمایشی `KOOCH_EVIDENCE_ORIGIN=http://127.0.0.1:3100` مجاز است. فرمان تا۲۶گام ادامه می‌دهد و در نخستین خطای شبکه/اعتبارسنجی متوقف می‌شود. اجرای دوباره checkpoint را ادامه می‌دهد. خروجی۲ یعنی دریافت کامل ولی بازبینی لازم؛ خروجی۱ خطاست. خطاهای provider و متن پاسخ خام چاپ نمی‌شوند.

اگر checkpoint ذخیره‌شده خراب شود، خواندن fail-closed می‌شود. مدیر دیتابیس می‌تواند ابتدا document همین namespace را export کند و فقط `checkpoint` آن را null کند؛ active، reviews و candidate حفظ شوند. سپس فرمان دستی اجرا شود. پاک‌کردن کل state یا جدول، راه بازیابی نیست چون صف شناخته‌شده را از بین می‌برد. در rollback برنامه، جدول و داده‌ها را حفظ کن؛ پاک‌کردن migration یا شواهد سابق لازم نیست.

## ترتیب عرضه

۱. افزونهٔ exporter روی سایت موجود نصب و REST/hash/cursor با دادهٔ عمومی آزموده شود.
۲. migration۰۰۶ روی همان دیتابیس محیط هدف اجرا و RLS/role بررسی شود.
۳. کلید مدیر و worker جدا، فقط برای همان محیط، تنظیم شوند؛ کلیدهای Preview به Production کپی نشوند.
۴. کد اپ منتشر و یک sync کامل دستی اجرا شود؛ تغییرات به صف بروند، نه فعال‌سازی خودکار قواعد.
۵. وضعیت مدیر، انقضا، دو مالک، گزارش قدیمی و روش rollback با دادهٔ مصنوعی پذیرفته شوند؛ سپس زمان‌بندی فعال شود.

این تیکت پیاده‌سازی و پذیرش محلی را انجام می‌دهد؛ provisioning کلیدها، نصب روی سایت تولید، migration تولید و فعال‌سازی schedule متعلق به عرضهٔ تیکت۱۰ است. نامزد عمومی و وضعیت sync از دادهٔ خصوصی متقاضی جدا می‌مانند.

## پذیرش محلی ۲۰۲۶-۱۰-۲۱

exporter در WordPress محلی با ۲ صفحه و ۲۹ مسیر، hash دقیق payload، حفظ تاریخ تأیید منابع و پاسخ410 برای cursor منقضی پذیرفته شد. همان خروجی PHP از API مصرف‌کنندهٔ Node و PostgreSQL واقعی عبور کرد: `ok` و پوشش جاری۲۹. تغییر مصنوعی شرط UK به صف رفت و پوشش جاری۲۸ شد. رابط مدیر در عرض۱۲۸۰ و۳۹۰ پیکسل RTL بود، کلید پس از درخواست خالی شد و سرریز افقی نداشت. fixture عمومی پس از بررسی بازگردانده شد.

۱۱۱ تست اپ، ۳۸۴ تست مخزن، ۴۷ تست Python، verify:release، check:static و build/typecheck موفق شدند. بازبینی Standards و Spec بدون یافتهٔ باز پایان یافت. تست‌های رگرسیون، استفاده از همان اتصال تراکنش در pool تک‌اتصالی، خطای sync مستقل از تغییر شواهد، و بازیابی cursor410 را پوشش می‌دهند. هیچ migration، کلید، افزونه یا زمان‌بندی Production در این پذیرش فعال نشده است.
