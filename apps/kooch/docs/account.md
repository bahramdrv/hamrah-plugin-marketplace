# حساب و ادامهٔ پرونده — برش ۰۲

انتخاب مالک در ۱۵ اکتبر ۲۰۲۶: Supabase Free برای Auth و PostgreSQL؛ SMTP جدا تعیین می‌شود. هیچ خرید یا ارتقای پولی مجاز نشده است. این پیاده‌سازی یک اتصال محلی واقعی دارد؛ وضعیت پروژهٔ میزبان و تحویل SMTP عمومی باید جدا ثبت شود.

## اجرای محلی مستقل

```sh
cd apps/kooch
npm ci
npm run account:setup
docker compose --env-file local/.env -f local/compose.yml up -d --wait
npm run account:migrate
npm run test:account
npm run build
npm start
```

رابط: `http://127.0.0.1:3100/account`؛ صندوق ایمیل آزمایشی: `http://127.0.0.1:58025`. از ایمیل و رمز ساختگی استفاده کن. رمز حداقل ۱۲ نویسه است. تأیید و بازیابی با ایمیل فارسی واقعی از Auth از طریق SMTP به Mailpit می‌رسند؛ Mailpit گیرندهٔ آزمایشی است و ایمیل را به اینترنت تحویل نمی‌دهد. پیوند یک‌بارمصرف باید در همان مرورگر باز و با دکمه مصرف شود. سرویس‌های db، Auth و mailbox فقط روی loopback پورت دارند؛ وب‌سرور قالب‌ها فقط در شبکهٔ داخلی containerهاست.

وابستگی‌های محلی تثبیت‌شده: PostgreSQL 18.4، Supabase Auth 2.197.0، Mailpit 1.31.6 و nginx 1.28. احراز هویت دست‌ساز یا ذخیرهٔ رمز در اپ وجود ندارد. Auth رسمی وظیفهٔ رمز، تأیید و بازیابی را دارد. رازهای محلی با randomBytes ساخته، با مجوز 0600 نوشته و از Git خارج شده‌اند. دستور setup فایل‌های موجود را بازنویسی نمی‌کند. Docker volume آزمایشی مستقل از وردپرس موجود است.

## گردش کار

۱. نتیجهٔ قطب‌نما همچنان پیش از ورود نمایش داده می‌شود. دکمهٔ ذخیره کاربر را به حساب می‌برد؛ هیچ پاسخ مهمانی با ثبت‌نام یا ورود خودکار وارد سرور نمی‌شود.
۲. پس از ورود، متن رضایت، حفظ ۹۰روزه و در صورت وجود پرونده، پیام جایگزینی پاسخ‌ها نمایش داده می‌شود. تنها دکمهٔ «ذخیره با اجازهٔ من» درخواست ذخیره می‌فرستد. پیش‌نویس مهمان پس از موفقیت انتقال از نشست حذف می‌شود.
۳. یک پروندهٔ فعال با owner سمت سرور، revision و request ID ذخیره می‌شود. تکرار همان درخواست نسخهٔ تازه یا فعالیت تازه نمی‌سازد؛ رقابت دو اصلاح فقط یک برنده دارد. پاسخ دیررس نسخهٔ فعال رابط را عوض نمی‌کند.
۴. ادامه از حساب، پاسخ‌ها را با نشست معتبر از سرور می‌خواند؛ ایمیل یا شناسهٔ مالک از URL پذیرفته نمی‌شود. در حالت پرونده، پاسخ‌ها فقط در حافظهٔ صفحه‌اند؛ ذخیرهٔ تغییرات اقدام جداست. خروج در تب دیگر حافظهٔ خصوصی را با BroadcastChannel پاک می‌کند.
۵. export فایل JSON خصوصی می‌دهد. حذف نیازمند رمز فعلی یا تأیید دوبارهٔ همان حساب گوگل و نوشتن عبارت «حذف حساب» است؛ ابتدا دسترسی با tombstone قطع و پرونده و رسیدهایش پاک می‌شوند، سپس هویت Auth حذف و نشست‌ها لغو می‌شوند. در صورت خطای provider، همان نشست فقط اجازهٔ تکرار حذف دارد و به پرونده دسترسی ندارد. tombstone فقط UUID حذف‌شده و وضعیت حذف Auth را نگه می‌دارد؛ ایمیل یا پاسخ ندارد و جلوی بازگشت داده را می‌گیرد.

## نشست و مالکیت

تمام APIهای حساب و خروجی خطا `no-store` و `Vary: Cookie` دارند. کوکی HttpOnly و SameSite=Strict است؛ حالت hosted همچنین Secure دارد و origin و endpoint Auth باید HTTPS باشند. نشست اپ یک شناسهٔ تصادفی دارد که تنها هش آن در DB است. توکن provider با AES-256-GCM و کلید محیطی ۳۲بایتی رمز می‌شود؛ refresh token یا رمز کاربر در اپ نگه داشته نمی‌شود. حداکثر نشست عادی یک ساعت و نشست محدود بازیابی ده دقیقه است؛ پس از انقضا ورود مجدد لازم است. هر درخواست خصوصی علاوه بر نشست زندهٔ اپ، کاربر تأییدشده را از Auth بررسی می‌کند. خروج و تغییر رمز همهٔ نشست‌های اپ همان حساب را فوراً لغو می‌کنند. نشست بازیابی اجازهٔ خواندن یا export پرونده ندارد.

دسترسی داده با دو لایه بررسی می‌شود: API owner را از نشست می‌گیرد؛ PostgreSQL با `SET LOCAL ROLE kooch_runtime` و تنظیم owner تراکنش، RLS را اعمال می‌کند. نقش runtime superuser یا BYPASSRLS نیست و RLS جدول پرونده و رسید درخواست FORCE شده است. اتصال اپ با نقش محدود `kooch_account_api` است؛ اتصال migration با credential جدا فقط برای اعمال schema استفاده می‌شود. استفاده از اتصال postgres مدیریتی به عنوان runtime هنگام راه‌اندازی رد می‌شود.

ثبت‌نام، ورود، بازیابی و بررسی پیوند دارای محدودیت اتمیک PostgreSQL هستند؛ کلید ایمیل/توکن در شمارنده HMAC است، نه متن خام. محدودیت provider نیز مستقل است. پیام خطای ورود و پاسخ بازیابی وجود یا عدم وجود ایمیل را آشکار نمی‌کنند. هیچ password، token، ایمیل یا پاسخ در log اپ چاپ نمی‌شود.

## نگهداری

`last_activity_at` فقط در ثبت/اصلاح پاسخ به‌روز می‌شود و `delete_after` دقیقاً ۹۰ روز بعد است. خواندن، export، ورود، خروج و پاک‌سازی آن را تمدید نمی‌کنند. پروندهٔ منقضی حتی قبل از job قابل خواندن نیست و در تراکنش همان owner پاک می‌شود. `npm run account:purge` پرونده‌های منقضی، نشست و شمارندهٔ منقضی را پاک می‌کند؛ برای میزبانی باید job محدود و زمان‌بندی آن ثبت شود. در این برش هیچ cron خارجی نصب نشده است. زمان نگهداری backup و محل پردازش به پروژهٔ Supabase منتخب وابسته‌اند؛ حذف آنی backup وعده داده نمی‌شود.

## اتصال Supabase Free و SMTP

سرویس میزبان هنوز باید واقعاً تنظیم و پذیرفته شود. مراحل مشخص اتصال:

- پروژهٔ Free منتخب، منطقه، سهمیه و وضعیت پرداخت/ارتقای خودکار ثبت شوند؛ پلن پولی فعال نشود.
- URL Auth برابر نشانی پروژه با پسوند `/auth/v1`؛ کلید publishable و secret (`sb_secret_`) فقط در env سرور، نه NEXT_PUBLIC. کلید secret فقط برای حذف Auth به کار می‌رود.
- schema با migration credential اعمال شود؛ برای `kooch_account_api` رمز مجزا تنظیم و آن نقش به رشتهٔ اتصال runtime داده شود. اتصال TLS و pooler با تنظیم واقعی پروژه بررسی شوند؛ رمز DB و کلید secret در چت نوشته نشوند.
- برای Supabase، گواهی ریشهٔ عمومی را از Database Settings → SSL configuration دریافت و متن PEM را در `KOOCH_DATABASE_CA_CERT` محیط سرور قرار دهید. `rejectUnauthorized` همیشه روشن می‌ماند؛ در نبود این متغیر، اعتماد پیش‌فرض Node استفاده می‌شود. [راهنمای رسمی SSL](https://supabase.com/docs/guides/platform/ssl-enforcement).
- Site URL و redirect فقط origin اپ انتخابی و `/account` باشند؛ ایمیل باید تأیید شود. قالب‌های فارسی `local/confirmation.html` و `local/recovery.html` در Auth میزبان تنظیم شوند؛ پیوندها با fragment `token_hash` و type هستند تا توکن به access log یا query نرود.
- SMTP عملیاتی و دامنهٔ فرستندهٔ تأییدشده انتخاب شود. دو ایمیل واقعی تأیید و بازیابی با حساب آزمایشی در صندوق گیرنده بررسی و رسید بدون توکن ذخیره شود. SMTP پیش‌فرض محدود Supabase جای اتصال عمومی نیست.
- `KOOCH_ACCOUNT_MODE=hosted`، origin HTTPS، URL/کلیدهای Auth، رشتهٔ اتصال runtime و کلید رمزگذاری مستقل روی سرور تنظیم شوند. کلید migration برای اجرای عادی لازم نیست.
- سناریوهای دو حساب، حذف، export، لغو نشست و no-store دوباره روی همان محیط اجرا شوند. بدون این شواهد، تیکت کاملِ اتصال عمومی محسوب نمی‌شود.

مبنای رفتار provider: [رمز و تأیید ایمیل](https://supabase.com/docs/guides/auth/passwords)، [محدودیت SMTP پیش‌فرض](https://supabase.com/docs/guides/auth/auth-smtp)، [Auth رسمی](https://github.com/supabase/auth)، [RLS PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

پروژهٔ میزبان در ۱۶ اکتبر ۲۰۲۶ در داشبورد تأیید شد: `kooch`، شناسهٔ `ifjtceqlcsmypuuflwlx`، سازمان `Kooch` با پلن Free، منطقهٔ `eu-west-1` (ایرلند). ساخت پروژه به‌تنهایی به معنی اتصال اپ یا پذیرش SMTP نیست؛ در زمان بررسی اولیه وضعیت زیرساخت `Coming up` بود.

در ادامهٔ همان روز، وضعیت پروژه `Healthy` شد و اسکریپت طرح حساب با تأیید مالک در SQL Editor اجرا شد: پنج جدول، دو سیاست RLS و دو نقش محدود ساخته شدند. پرس‌وجوی مستقل FORCE RLS پرونده/رسید، نبود superuser/BYPASSRLS در هر دو نقش و عدم USAGE نقش‌های anon/authenticated روی schema خصوصی را تأیید کرد. رمز نقش اپ هنوز تعیین نشده و اتصال runtime هنوز پذیرفته نشده است. Site URL برابر `https://my.kooch.app/account` و حداقل رمز برابر ۱۲ نویسه ثبت شدند؛ تأیید ایمیل فعال ماند. دامنه هنگام بررسی DNS پاسخ نداد. تغییر قالب‌های ایمیل در داشبورد تا تنظیم SMTP سفارشی در دسترس نیست. Resend فقط بررسی شده، متصل نشده است.

اصلاح اتصال کلیدهای جدید: در درخواست مدیریتی، کلید `sb_secret_` فقط در هدر `apikey` فرستاده می‌شود؛ نشست کاربر همچنان Bearer مستقل دارد. JWT سرویس محلی نیز پشتیبانی می‌شود. [مستند Supabase](https://supabase.com/docs/guides/getting-started/api-keys) استفاده از کلیدهای جدید را به جای JWT قدیمی توصیه می‌کند. دو آزمون این مرز شامل شکست اولیهٔ کلید جدید و سپس عبور هر دو حالت ثبت شدند.

## ورود گوگل

دکمهٔ «ادامه با گوگل» پس از تنظیم Google provider در Supabase و قرار دادن `KOOCH_GOOGLE_AUTH_ENABLED=true` روی سرور ظاهر می‌شود. کلید Google Client Secret فقط در تنظیم provider پروژهٔ Supabase ذخیره می‌شود؛ اپ آن را دریافت نمی‌کند.

در Google Cloud، یک OAuth client از نوع Web application با origin برابر `https://my.kooch.app` و redirect URI برابر `https://ifjtceqlcsmypuuflwlx.supabase.co/auth/v1/callback` ساخته شود. فقط scopeهای `openid`، ایمیل و پروفایل لازم‌اند. در URL Configuration پروژهٔ Supabase، نشانی دقیق `https://my.kooch.app/api/account/google-callback` به redirect allow list اضافه شود. فعال‌سازی عمومی Google تا تنظیم audience و آزمون واقعی ورود، تأییدشده نیست. [راهنمای رسمی گوگل در Supabase](https://supabase.com/docs/guides/auth/social-login/auth-google).

شروع ورود یک POST از origin خود اپ است. verifier تصادفی PKCE در cookie کوتاه‌عمر HttpOnly با امضای سرور و SameSite=Lax می‌ماند؛ مرورگر فقط challenge را به Auth می‌برد. callback کد یک‌بارمصرف را سمت سرور مبادله می‌کند، cookie موقت را پاک و نشست عادی حساب را با همان owner تأییدشده ایجاد می‌کند. access/refresh token وارد JavaScript یا storage نمی‌شوند؛ مقصد برگشت ثابت است و خطاهای provider به صفحه یا log بازتاب نمی‌شوند. Google OAuth و ایمیل/رمز از کنترل مالکیت، خروج و نگهداری یکسان استفاده می‌کنند.

وضعیت میزبانی در ۱۷ اکتبر ۲۰۲۶: اتصال محدود PostgreSQL، HTTPS دامنهٔ نهایی و SMTP Resend با فرستندهٔ `noreply@kooch.app` برقرار شدند. قالب‌های فارسی تأیید و بازیابی ذخیره و ایمیل تأیید با وضعیت Delivered و تأیید/ورود مالک در Auth مشاهده شد. پذیرش بازیابی، چرخهٔ کامل پرونده، جداسازی دو حساب و job نگهداری میزبانی هنوز باز است. ورود گوگل تا فراهم‌شدن client رسمی Google Cloud و آزمون واقعی provider عملیاتی اعلام نمی‌شود.

تأیید دوبارهٔ گوگل برای حذف، مجوز امضاشدهٔ پنج‌دقیقه‌ای متصل به UUID مالک و هش همان نشست اپ می‌دهد. بازگشت گوگل به‌تنهایی حذف نمی‌کند؛ ارسال دوبارهٔ عبارت تأیید لازم است. مجوز روی نشست یا حساب دیگر پذیرفته نمی‌شود. درخواست callback نامعتبر سهمیهٔ کاربران دیگر را مصرف نمی‌کند.
