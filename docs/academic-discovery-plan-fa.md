# برنامهٔ Hamrah Academic Discovery

تاریخ: ۱ اکتبر ۲۰۲۶. وضعیت: تصمیم‌های Q1 تا Q8 تأیید شده‌اند؛ برنامهٔ کامل توسط مالک تأیید شده و پیاده‌سازی در جریان است. این سند گزارشِ پیاده‌سازی یا فعال‌سازی قابلیت جدید نیست.

## هدف و تصمیم‌های تأییدشده

Hamrah باید از اطلاعات محدود هم خروجی اکتشافی مفید بدهد و با اطلاعات کافی، تطبیق دانشگاهی مستند ارائه کند. قالب و قواعد مقایسه ثابت باشند؛ نتیجه با شواهد جاری به‌روز شود و دلیل تغییر مشخص باشد. پوشش کامل جهان و درست‌بودن همیشگی نتیجه قابل تضمین نیست؛ کمبود شواهد، خطای منبع و زمان بررسی باید قابل مشاهده باشند.

مالک در این گفتگو این تصمیم‌ها را تأیید کرده است:

- Q1: قالب و قواعد ثابت؛ نتیجهٔ به‌روز با تغییرهای مشخص؛ نسخهٔ قبلی قابل بازبینی.
- Q2: نتایج تأییدشده در بخش اصلی؛ سرنخ‌های مرتبط در بخش جدا با وضعیت نیازمند بررسی.
- Q3: پس از محدودیت‌های قطعی، ارتباط پژوهشی معیار اصلی است؛ فاند و امکان اقدام جدا نمایش داده شوند. درخواست «فقط دارای فاند» شرط قطعی است.
- Q4: مخزن مشترک فقط دادهٔ عمومی؛ گزارش و پروفایل شخصی در گفتگو یا فایل خروجی. [ADR 0008](adr/0008-public-academic-data-private-reports.md).
- Q5: اطلاعات ناکافی مانع خروجی اکتشافی نباشد؛ محدودیت تطبیق و اطلاعات موردنیاز روشن باشند.
- Q6: ROR، OpenAlex، Crossref، اتصال‌های رسمی/ATS و JSearch موجود، به‌همراه Tavily و جستجوی وب انتخاب شدند.
- Q7: Redis موجود با ذخیرهٔ محدود و دارای انقضا گسترش یابد؛ کاتالوگ دائمی PostgreSQL جزء فاز اول نیست. [ADR 0009](adr/0009-bounded-academic-discovery-store.md).
- Q8: پاسخ اولیه حداکثر ۱۰ گزینهٔ اصلی با سرنخ‌های جدا؛ بررسی بیشتر ادامهٔ همان جستجو باشد و دامنهٔ واقعی نمونه‌برداری اعلام شود.
- جستجوی وب هرجا لازم باشد ادامه دارد؛ API جای آن را نمی‌گیرد.

## منابع انتخاب‌شدهٔ فاز اول

| نیاز | منابع | نقش و حد ادعا |
| --- | --- | --- |
| هویت دانشگاه | [ROR](https://ror.readme.io/docs/rest-api) + OpenAlex institution | نام، شناسه و سایت سازمان؛ دلیل وجود برنامه یا پذیرش نیست |
| استاد و پژوهش | [OpenAlex](https://help.openalex.org/api/authentication/): works/authors/topics | کشف ارتباط پژوهشی؛ سمت فعلی و جذب دانشجو از دانشگاه بررسی می‌شود |
| مقاله و DOI | [Crossref](https://www.crossref.org/documentation/retrieve-metadata/rest-api/) | تطبیق DOI و metadata؛ متن abstract خودکار ذخیره نشود |
| برنامهٔ تحصیلی | صفحهٔ رسمی دانشگاه + دادهٔ ملی مشخص مانند Studyinfo | عنوان، مقطع، زبان، شرایط و intake؛ OpenAlex کاتالوگ پذیرش نیست |
| موقعیت باز | اتصال‌های رسمی و ATS موجود + [JSearch](https://www.openwebninja.com/api/jsearch) | JSearch سرنخ چندکشوری است؛ coverage دانشگاهی کامل ندارد |
| بورسیه و stipend | جستجوی وب و صفحهٔ رسمی فراخوان | شرایط، مهلت و ارتباط با پذیرش باید مستقل تأیید شوند |
| سابقهٔ گرنت | [OpenAlex Awards](https://help.openalex.org/data/awards/) و منبع اصلی در صورت نیاز | سابقهٔ گرنت اعطاشده؛ فاند آزاد یا جذب دانشجو را ثابت نمی‌کند |
| جستجوی وب | [Tavily Free](https://www.tavily.com/pricing) + جستجوی میزبان هنگام نیاز | سرنخ و URL؛ پاسخ تولیدشدهٔ provider مدرک نهایی نیست |

OpenAlex برای استفادهٔ پایه بدون کلید قابل استفاده است؛ کلید رایگان بودجه را بیشتر می‌کند. ROR و Crossref به ثبت‌نام برای public read نیاز ندارند. ORCID Public API به‌دلیل [محدودیت استفادهٔ تجاری](https://info.orcid.org/public-client-terms-of-service/) وابستگی فاز اول نمی‌شود؛ فایل CC0 سالانه در صورت نیاز هویتی بررسی خواهد شد. OpenAIRE، NIH، NSF، UKRI و CORDIS زمانی adapter جدا می‌گیرند که شکاف مشخص پوشش نشان داده شود.

Tavily در زمان بررسی ۱۰۰۰ credit ماهانه بدون کارت ارائه می‌کند. پیشنهاد تنظیم اولیه: basic، `auto_parameters=false`، `include_answer=false`، `include_raw_content=false`، بدون تصاویر و با بودجهٔ مشخص. [قرارداد API](https://docs.tavily.com/documentation/api-reference/endpoint/search). این سهمیه ظرفیت نامحدود محصول نیست و [Terms](https://www.tavily.com/terms) جای اجازهٔ نگهداری محتوای ثالث را نمی‌گیرد.

حساب JSearch از قبل موجود است؛ [راهنمای فعلی](jsearch-setup-fa.md) Basic $0، سهمیهٔ ۲۰۰ و hard limit را ثبت کرده. در این کار حساب دیگری ساخته نشده. شرایط OpenWeb Ninja [ثبت‌نام خودکار](https://www.openwebninja.com/terms) را منع می‌کند؛ حساب جدید این سرویس باید توسط مالک ایجاد شود. کلیدها فقط در Secretهای Vercel قرار می‌گیرند، نه گزارش، Git یا چت.

## روند هر درخواست

1. درخواست صریح کاربر نوع جستجو را تعیین می‌کند: دانشگاه، برنامه، استاد، فراخوان پذیرش، موقعیت پژوهشی یا بورسیه. اطلاعات معلوم جدا از نامعلوم ثبت می‌شوند؛ جزئیات حدس زده نمی‌شوند.
2. رشته و موضوع به واژگان canonical و مترادف‌های ثبت‌شده تبدیل می‌شوند. برای مثال «هوش مصنوعی»، AI و artificial intelligence باید query plan قابل مقایسه داشته باشند. انتخاب مترادف و نسخهٔ آن ثبت می‌شود.
3. plan محدود، منابع، کشورها، queryها و بودجه را تعیین می‌کند. در درخواست بی‌کشور، نمونه‌برداری صریح است؛ آن را worldwide coverage نمی‌نامیم.
4. API و مخزن عمومی سرنخ می‌دهند؛ جستجوی وب شکاف‌ها و صفحات رسمی را پیدا می‌کند. ارسال به provider محدود به نوع جستجو، رشته، موضوع و کشور است؛ نام، رزومه و مشخصات خصوصی متقاضی ارسال نمی‌شوند.
5. هویت سازمان با ROR/دامنهٔ مستند و هویت رکورد با شناسهٔ ناشر و URL canonical حل می‌شود. دو URL مختلف یک آگهی، دو نتیجه محسوب نمی‌شوند؛ تشابه نام به‌تنهایی برای merge کافی نیست.
6. صفحهٔ دقیق رسمی در درخواست جاری دریافت می‌شود. هر ادعای تعیین‌کننده، URL، زمان بررسی و شاهد همان ادعا را دارد. مهلت آینده به‌تنهایی کافی نیست اگر منبع بسته‌شدن را اعلام کرده باشد. پاسخ ناقص، 403 یا timeout به unknown تبدیل می‌شود.
7. محدودیت‌های قطعی اعمال می‌شوند. پژوهش مرتبط، بازبودن پذیرش، فاند و محدودیت ملیت مستقل‌اند. شرط مبهم یا نبود اشاره به ایران، امکان قطعی اقدام ایرانیان نیست؛ غربال تحریم خودکار هم تصمیم حقوقی نیست.
8. نتایجِ همان نوع با قواعد نسخه‌دار و tie-break پایدار مقایسه می‌شوند. دانشگاه، استاد و بورس در یک رتبهٔ مبهم مخلوط نمی‌شوند؛ درصد شانس پذیرش تولید نمی‌شود.
9. یک renderer فارسی، JSON معتبر و متن قابل نمایش را از دادهٔ واحد می‌سازد؛ مدل میزبان نباید ترتیب و وضعیت‌های تأییدشده را دوباره بسازد.
10. گزارش شخصی به گفتگو/فایل برمی‌گردد. اجرای بعدی، در صورت داشتن گزارش قبلی، تغییرهایی مانند بسته‌شدن یا عوض‌شدن مبلغ فاند را با دلیل نشان می‌دهد؛ سرور تاریخچهٔ شخصی نگه نمی‌دارد.

## قرارداد خروجی پیشنهادی

Envelope مشترک شامل `schemaVersion`، `reportId`، `checkedAt`، `scope`، `inputCompleteness`، `policyVersions`، `coverage`، `verifiedResults`، `discoveryCandidates`، `exclusions`، `changes` و `nextActions` است. جزئیات هر نوع، schema اختصاصی دارد؛ وضعیت‌های برنامه با موقعیت باز یکسان‌سازی معنایی نمی‌شوند.

برای هر نتیجه: شناسهٔ پایدار، نوع، عنوان، دانشگاه/ROR، کشور، لینک رسمی، وضعیت تأیید، زمان بررسی، دلیل ارتباط پژوهشی، شرایط معلوم و نامعلوم، وضعیت فاند، اطلاعات deadline و شواهد ادعاها. scope و منبعِ نتیجه نیز مشخص‌اند.

قالب قابل مشاهدهٔ هر گزارش:

1. درخواست فهمیده‌شده، تاریخ بررسی و اطلاعات ناقص.
2. نتایج تأییدشده با ستون‌های ثابت و دلیل تطبیق.
3. سرنخ‌های مرتبط و دلیل تأییدنشدن.
4. منابع و کشورهایی که واقعاً بررسی شدند؛ شکست‌ها و محدودیت صفحه‌بندی.
5. تغییر نسبت به گزارش قبلی، اگر گزارش قبلی ارائه شده باشد.
6. اقدام بعدی متناسب با همان نتیجه.

نمونهٔ زیر صرفاً نمایش قرارداد است و نتیجهٔ واقعی نیست:

| گزینه | نوع | ارتباط پژوهشی | وضعیت اقدام | فاند | مدرک |
| --- | --- | --- | --- | --- | --- |
| نمونهٔ A | موقعیت دکتری | موضوع مشخص با شاهد رسمی | باز تا تاریخ مشخص | حقوق مستند؛ مبلغ نامعلوم | URL دقیق + تاریخ بررسی |
| نمونهٔ B | سرنخ استاد | مقالهٔ مرتبط | جذب دانشجو تأیید نشده | نامعلوم | صفحهٔ دانشگاه + metadata مقاله |

تکرارپذیری دقیق یعنی ورودی canonical، شواهد/زمان مرجع و نسخهٔ قواعد یکسان، خروجی یکسان بدهند. دادهٔ زنده در دو روز مختلف می‌تواند نتیجه را تغییر دهد. هم‌ارزی معنایی ورودی، ترتيب provider و jitter دریافت نباید به‌تنهایی ترتیب نتیجه را عوض کنند. بستهٔ بازبینی خصوصی در فایل، ورودی و شواهد مجاز را کنار نسخهٔ قواعد نگه می‌دارد؛ مخزن مشترک فقط manifest عمومی مجاز را ذخیره می‌کند.

## دیتابیس و Vercel

انتخاب مالک استفاده از Redis موجود با namespaceهای مستقل است؛ PostgreSQL/pgvector پیش‌نیاز دقت نیستند. CC0 و metadata واقعی دارای مبنای نگهداری، طبق سیاست منبع ذخیره شوند. ذخیرهٔ snippets جستجو، متن کامل آگهی و contact list خودکار مجاز شمرده نشود. سیاست هر منبع باید fields، مجوز، attribution، TTL، حذف، حداکثر bytes و سهمیه را مشخص کند.

ADR 0006 برای نام استاد و ADR 0007 برای JobTech حفظ می‌شوند؛ مخزن عمومی جدید نیازمند سیاست خودش است. تمدید TTL نام قدیمی با merge تازه باید با عمر واقعی رکورد جایگزین یا صریحاً مستند شود. کش hit هیچ وضعیت تأیید را از اجرای قبل به اجرای جدید منتقل نمی‌کند.

Vercel فعلی maxDuration=60 دارد، ولی deadline ابزار پیش‌فرض ۲۵ ثانیه است؛ افزایش maxDuration به‌تنهایی orchestration را حل نمی‌کند. fan-out محدود و deadline مرحله‌ای لازم است تا قبل از timeout، خروجی صادقانهٔ جزئی برگردد. ادامهٔ بررسی از state عمومی و token فاقد اطلاعات خصوصی استفاده کند. refresh زمان‌بندی‌شده و crawl عمومی وسیع جزء پیش‌فرض فاز اول نیست.

در rollout: Secret منبع جدید در Preview و سپس Production؛ flagهای اتصال مستقل؛ امکان خاموش‌کردن منبع مشکل‌دار؛ اندازه‌گیری مصرف مشترک Redis و API؛ هیچ ارتقای پولی یا overage خودکار. تغییر env برای deployment جدید آزمایش می‌شود. rollback باید با flags و نسخهٔ قبلی قابل انجام باشد. push به Git فقط با درخواست مالک است.

## معیار پذیرش

- test-first در executeTool و reader/validatorهای عمومی؛ دادهٔ زمان و provider در replay ثابت باشند.
- یک ورودی یکسان و شواهد ثابت دو بار، JSON و متن یکسان تولید کند؛ ورودی‌های فارسی و انگلیسیِ هم‌معنا نتایج قابل مقایسه بدهند.
- queryها و metadata استاندارد شوند؛ URL tracking و ترتیب دریافت نتیجهٔ تکراری یا رتبهٔ متفاوت ایجاد نکنند.
- snippet API بدون دریافت رسمی نتواند فرصت را verified کند؛ استاد مرتبط بدون recruitment evidence جذب‌کننده معرفی نشود.
- گرنت فعال، بورس دانشجویی یا حقوق تضمین‌شده نسازد؛ فاند رقابتی از فاند تضمین‌شده جدا باشد.
- انقضا، بسته‌شدن، حذف و تضاد منابع رتبه/وضعیت را درست تغییر دهند و دلیل تغییر ثبت شود.
- سهمیه/timeout/403/429 و database outage پوشش را صادقانه کاهش دهند؛ خالی‌شدن نتیجه به معنی نبود فرصت نباشد.
- payload provider، دیتابیس و logs شامل پروفایل، نام یا کلید خصوصی نباشند.
- benchmark کوچکِ ازپیش‌ثبت‌شده با موارد مثبت، منفی و نامعلومِ تمام انواع؛ دقت verified claims، خطای unknown، پوشش و زمان p50/p95 اندازه‌گیری شود. ادعای دقت عددی پیش از اندازه‌گیری ارائه نشود.
- live acceptance با SHA دقیق، API واقعی، exact official pages و بررسی expiry/concurrency Redis؛ smoke مصنوعی فقط قرارداد را اثبات می‌کند.

## بررسی‌های انجام‌شده در همین گفتگو

- `npm test`: ۳۴۷ موفق. اجرای sandbox، ۱۳ خطای EPERM برای listen localhost داشت؛ تکرار با مجوز اجرای تست بیرون sandbox کامل موفق شد.
- `npm run verify:release`: ۱۹ schema و ۵۷ dataset منتشرشده، یکی withdrawn؛ موفق.
- `npm run check:static`: موفق.
- چهار suite Python با `/opt/anaconda3/bin/python`: ۴۷ موفق؛ هیچ بسته‌ای نصب نشد.
- `verify-live-opportunities.mjs` با SHA دقیق بالا: قرارداد خروجی فرصت/فراخوان مصنوعی موفق. حالت unavailable آن smoke عمداً کشور/نوع بدون پوشش را می‌سنجد؛ نشانهٔ خاموش‌بودن همهٔ APIها نیست.
- یک درخواست واقعی `discoverAcademicCallCandidates` با `Physics/phd/US` و limit=3 در همان نسخه: HTTP 200 و نتیجهٔ partial؛ منبع `jsearch:openwebninja` فعال، صفر candidate و خطای `jsearch_source_failed`. فعال‌بودن config احراز شد؛ دریافت موفق دادهٔ JSearch احراز نشد. علت خطا باید با تشخیص امن، بدون افشای پاسخ حساس یا کلید، روشن و پس از اصلاح دوباره اجرا شود. این نتیجه اثبات نبود موقعیت نیست.

## ترتیب اجرا و مرز تکمیل

هفت ticket در [نقشهٔ کار](../.scratch/academic-discovery-orchestration/map.md) ایجاد شده‌اند: قرارداد مشترک و query، اتصال منابع و وب، مخزن عمومی، تأیید رسمی و orchestration، تطبیق و نمایش فارسی، benchmark و پذیرش، سپس rollout Vercel.

اتصال منابع موجود از ابتدا حفظ می‌شود؛ شکست JSearch پیش از اتکا به آن تشخیص داده می‌شود. ساخت حساب Tavily/OpenAlex فقط در صورت نیاز و طبق شرایط خود سرویس انجام می‌شود. مرحلهٔ پذیرش شرایط حساب یا احراز هویتِ نیازمند دخالت مالک، یک مانع مشخص راه‌اندازی است و نباید به ادعای «وصل شد» تبدیل شود.

کار زمانی کامل است که جریان انتخاب‌شده در Preview و Production با API واقعی، صفحهٔ رسمی واقعی، گزارش فارسی واحد و مصرف ثبت‌شده قبول شود؛ موفقیت تست‌های موجود تنها خط مبناست. هیچ پوشش جهانی یا درصد دقت اندازه‌گیری‌نشده وعده داده نمی‌شود.

مالک در همین گفتگو درک مشترک برنامهٔ کامل و استفاده از حساب رایگان Tavily را تأیید کرد. پیاده‌سازی و آزمون پذیرش Preview انجام شده‌اند؛ نتیجهٔ دقیق انتشار و محدودیت‌ها در academic-discovery-acceptance.md ثبت می‌شوند.
